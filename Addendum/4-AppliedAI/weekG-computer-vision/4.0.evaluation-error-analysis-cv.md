# Week G — Day 4: Seeing What the Model Sees — Evaluation & Error Analysis for CV
> Pairs with `4.1.evaluation-error-analysis-cv.py`

## 📚 Topics
Beyond accuracy for images: per-class metrics, confusion structure, confidence analysis, Grad-CAM
(where did it LOOK?), systematic error hunting (slicing), robustness probes (corruptions), test-set hygiene.

## 🎯 Learning Goals
1. Produce the full evaluation kit for Day-3's best model: per-class precision/recall (Week 3/5 metrics,
   image edition), confusion matrix with the top confused PAIRS visualized as image grids.
2. Implement Grad-CAM at mechanics level: gradients of the class score w.r.t. the last conv feature maps →
   weight the maps → heatmap of "where the evidence was". (It's Week D-6 gradients, repurposed for seeing.)
3. Hunt SYSTEMATIC errors by slicing: accuracy by brightness/contrast/object scale buckets — find at least
   one slice where the model is measurably worse, then explain it (often an augmentation gap → fix → re-measure: the full loop).
4. Probe robustness: accuracy under blur/noise/JPEG corruption at 3 severities — the gap between benchmark
   accuracy and the real world, measured.
5. Audit confidence: reliability curve for the CNN (Week B-4 returns — deep nets are famously overconfident;
   temperature scaling as the one-knob fix).

## 🛠️ Build in the paired .py
1. The evaluation kit function (per-class table + confusion matrix + worst-pairs image grids) — reusable, it
   ships again in Week I and Module 5.
2. Grad-CAM (~30 lines with hooks; no library) + heatmaps for 6 correct and 6 wrong predictions; at least one
   "right answer, WRONG evidence" case if you can find it (the most important find in interpretability).
3. The slicing study + the fix-and-remeasure loop documented.
4. Corruption grid (3 corruptions × 3 severities → 9 accuracies, heatmapped).
5. Reliability curve + temperature scaling on validation; Brier before/after (Week B-4 code, reused verbatim).

## ⚠️ Common Mistakes
Grad-CAM treated as proof rather than evidence · slicing on test until something "interesting" appears
(multiple comparisons — Week D-2 p-hacking demo, image edition!) · fixing test-set failures BY LOOKING at test
(that data is spent; fix via train/val).
