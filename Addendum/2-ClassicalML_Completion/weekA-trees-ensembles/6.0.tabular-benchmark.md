# Week A — Day 6: The Tabular Benchmark — Linear vs Trees vs Boosting
> Pairs with `6.1.tabular-benchmark.py`

## 📚 Topics
Honest multi-model comparison at scale, dataset-dependence of rankings, cost columns, the
"GBM usually wins tabular" claim tested on YOUR data.

## 🎯 Learning Goals
1. Design a comparison protocol BEFORE running: fixed splits, fixed metric (+CI), fixed tuning budget per
   family — write it down first (pre-registration, qb-week8 Tricky-5).
2. Produce a defensible league table: LogReg, single tree, RF, GBM, XGB/LGBM across 3+ datasets.
3. Observe and explain ranking flips between datasets (n, dimensionality, signal linearity, noise).
4. Add cost columns (fit time, predict time, model size) and argue a deployment choice that is NOT the top scorer.
5. Interpret "no free lunch" concretely from your own table.

## 🔍 Core Mechanics / Protocol
- Datasets: Titanic (cached), one mid-size OpenML tabular (e.g., adult income), one synthetic linear-dominant
  (`make_classification` with informative linear structure) — the last one is where LogReg should WIN; predict it.
- Per family: identical 5-fold StratifiedKFold, identical RandomizedSearch budget (e.g., 25 draws), ROC-AUC primary.
- Report: mean ± std per cell; bold within-dataset winners; bootstrap CI for the top-two gap on each dataset.

## 🛠️ Build in the paired .py
1. The harness: `run_family(model, param_dist, X, y) -> dict` so every family flows through identical code.
2. The league table as a DataFrame → markdown (reuse the qb-week8 challenge-5 generator idea).
3. The cost columns + a scatter of score vs fit-time (the efficient frontier).
4. A 15-line written verdict: when did boosting win, when didn't it, what would you try first on a NEW tabular problem now.

## ⚠️ Common Mistakes
- Unequal tuning budgets (the model you love gets more search = silent rigging).
- Declaring winners on differences inside the noise (your CIs exist; use them).
- Forgetting predict-latency matters more than fit-latency in production.
