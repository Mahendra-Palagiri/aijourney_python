# Week K — Day 5: Monitoring & Drift — The Model Met Reality; Reality Moved
> Pairs with `5.1.monitoring-drift.py`

## 📚 Topics
Why deployed models decay (the world changes, the model doesn't), the monitoring stack: system metrics
(latency/errors), data quality (schema, nulls, ranges), input drift (distributions shift), prediction drift,
and — when labels arrive late — performance drift; drift detection math (PSI, KS test — Week D-2 pays off);
alert design; the retraining decision.

## 🎯 Learning Goals
1. Build the four-layer monitoring mental model (system → data quality → drift → performance) and know which
   layer FAILS FIRST and which you can measure SOONEST (labels lag — that's the whole game: drift is the
   early-warning proxy for performance you can't yet see).
2. Implement drift math from scratch: PSI (binned distribution comparison; the >0.2 rule of thumb and its
   arbitrariness acknowledged) and the KS test (Week D-2's machinery, deployed); per-feature drift table.
3. Connect to old friends: drift detection IS Week C-7/H-6 anomaly thinking on the input stream; multiple
   features tested = multiple comparisons (Week D-2's p-hacking demo — alert thresholds must account for it
   or you'll cry wolf weekly).
4. Simulate the lifecycle honestly: train on period A → "deploy" → feed period B with injected shifts
   (gradual, sudden, feature-broken) → watch each monitor catch (or miss) each shift type.
5. Design the retraining policy: triggered by what (drift score? schedule? performance once labels arrive?),
   retrain on what window, validated how before promotion (shadow mode! Day 4's design slots in) — write it
   as a runbook, the document on-call-you will thank planning-you for.

## 🛠️ Build in the paired .py
1. `drift_report(reference_df, current_df)`: PSI + KS per feature + prediction-distribution comparison → markdown report (your Week-8 report-generator habit, productionized).
2. The simulation: 3 shift types × the report — a 3×N caught/missed matrix with commentary.
3. Logging middleware addition to Day-2's API: every request's features + prediction + latency to a log table (the monitoring data source).
4. The alert-threshold experiment: false-alarm rate on UNshifted data at various PSI cutoffs (multiple-comparisons, measured).
5. The retraining runbook (1 page, committed).

## ⚠️ Common Mistakes
Monitoring accuracy when labels won't arrive for months (monitor what you can SEE now) · per-feature alerts
with no family-wise thinking (alert fatigue → ignored alerts → the one real one missed) · drift detected,
no runbook (a graph nobody acts on is decoration).
