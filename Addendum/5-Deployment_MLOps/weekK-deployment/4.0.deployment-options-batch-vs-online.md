# Week K — Day 4: Deployment Patterns — Batch vs Online, and Where Containers Go
> Pairs with `4.1.deployment-options-batch-vs-online.py`

## 📚 Topics
The deployment decision tree: batch scoring vs online API vs streaming vs edge (on-device); cost/latency/
freshness trade-offs; where containers actually run (a VM, a PaaS, serverless, k8s — survey honestly, deploy
small); scheduled jobs (cron); the batch-scoring pipeline pattern; blue/green & canary at concept level.

## 🎯 Learning Goals
1. Internalize the FIRST question of deployment: "does the prediction need to exist before the request, or
   after?" — batch (score nightly, store results, serve lookups: most business ML!) vs online (compute on
   demand: Day 2's API) — map 6 scenario cards to patterns with costs.
2. Build the batch pattern fully: cron-style script → read new rows from db (Week J-3) → predict via the
   SAME `predict()` (one brain, two doors — never fork the logic) → write predictions table with model
   version + timestamp → idempotency (re-runs don't duplicate).
3. Deploy the container ONCE somewhere real (a free-tier PaaS or a local VM): env vars for config, the
   public /health check, a remote smoke test — demystify "production" by touching it.
4. Understand rollout safety at concept level: blue/green (two environments, switch), canary (1% traffic
   first), and the ML-specific shadow mode (new model predicts silently alongside old; compare offline) —
   shadow mode is the one you'll actually use; design (not run) one for Week-I's model.
5. Write the deployment one-pager for the Week-I model: pattern chosen, why, costs, rollback plan.

## ⚠️ Common Mistakes
Online APIs built where nightly batch was the honest answer (resume-driven architecture) · scoring logic
duplicated between batch and API (skew incubator) · no rollback story until the day it's needed.
