# Week K — Day 6: Integration Day — The Serving Stack, Assembled & Defended
> Pairs with `6.1.serving-week-integration.py`

## 📚 Topics
Assembly of Days 1–5 into one coherent, tested, containerized, monitored service; load behavior; the
serving defense document.

## 🎯 Learning Goals
1. Assemble the full stack for ONE model (Week I's, ideally): artifact (D1) → API (D2) → container (D3) →
   deployed/composed (D4) → logging + drift report wired (D5) — every component already exists; today is
   plumbing and PROOF.
2. Characterize behavior under load: the smoke-load at 3 levels; latency percentiles table; find the first
   bottleneck (it's usually feature preprocessing — profile, Week G-5 habit); one optimization, re-measured.
3. Run the failure drill: kill the db mid-request, send malformed payloads, load a wrong-version artifact —
   verify every failure is CAUGHT, LOGGED, and returns a clean error (chaos engineering, kindergarten edition — the most fun day of the module).
4. Write `weekK_serving_defense.md`: architecture diagram (mermaid — Week 3/11 tooling), contract, latency
   table, failure-mode matrix (failure → detection → response), monitoring coverage, known limits.
5. Tag a release (Week J-5's semver): `serving-v0.1.0` — the artifact Week M builds on.

## 🛠️ Deliverables
- [ ] Running composed stack (one command up) · - [ ] Load table + bottleneck fix · - [ ] Failure-drill matrix
- [ ] `weekK_serving_defense.md` with diagram · - [ ] Tagged release · - [ ] CI green on all of it

## ⚠️ Common Mistakes
Integration "by hope" (each pairwise connection gets a test) · skipping the failure drill (failures WILL run
it for you later, unsupervised) · the defense doc describing the system you MEANT to build (describe the one that exists).
