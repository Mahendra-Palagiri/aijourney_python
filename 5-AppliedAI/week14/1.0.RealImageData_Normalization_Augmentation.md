## 4. From Image File to Training Batch

### 4.1 The Complete Path

A real image usually passes through several representations:

```text
JPEG or PNG file
→ decoded image
→ PIL image
→ geometric and color transformations
→ PyTorch tensor [C, H, W]
→ normalization
→ batch tensor [N, C, H, W]
→ model
```

| Stage | Responsibility |
|---|---|
| File | Stores compressed image data |
| Decoder/PIL | Converts stored bytes into accessible pixels |
| Geometric transforms | Adjust size, crop, orientation, or position |
| Tensor conversion | Produces numeric PyTorch data |
| Normalization | Changes each channel’s numeric distribution |
| DataLoader | Collects samples into batches |
| Model | Learns from the processed tensors |

Resizing changes spatial dimensions, normalization changes numeric values, and batching adds a new dimension.

### 4.2 Files Are Not Tensors

A JPEG file is a compressed representation. A CNN cannot directly perform convolution on JPEG bytes.

An image-loading library first decodes the file into pixels. In many `torchvision` workflows, the decoded result is a PIL image.

A PIL RGB image commonly has the conceptual layout:

```text
height × width × channels
```

After `ToTensor()`, PyTorch uses:

```text
channels × height × width
```

An RGB image resized to `224 × 224` has the shape:

```text
[3, 224, 224]
```

A batch of 32 such images has the shape:

```text
[32, 3, 224, 224]
```

The `DataLoader` adds the first dimension.

### 4.3 Tensor Conversion Also Rescales Pixels

Ordinary 8-bit images usually store each color value as an integer between `0` and `255`.

`transforms.ToTensor()` normally converts these values to floating-point numbers and rescales them into approximately `[0, 1]`.

```text
Scaled pixel = Original pixel ÷ 255
```

For example:

```text
128 ÷ 255 ≈ 0.502
```

This is **pixel scaling**, but it is not yet statistical normalization:

```text
ToTensor:
255 → 1.0

Normalize:
1.0 → a value based on the channel mean and standard deviation
```

## 5. Creating Consistent Spatial Dimensions

### 5.1 Why Images Need Compatible Sizes

Real images do not naturally share one size or aspect ratio:

```text
640 × 480
1920 × 1080
300 × 900
224 × 224
```

A batch is one rectangular tensor, so all images in that batch must have the same height and width.

Common spatial-processing options include:

- direct resizing,
- resize followed by cropping,
- random resized cropping,
- padding,
- or variable-size batching with custom logic.

For ordinary image classification, resizing and cropping are common starting points.

### 5.2 Direct Resize

A direct resize forces every image to an exact output size:

```python
transforms.Resize((224, 224))
```

This is simple and deterministic, but it may distort the original aspect ratio. Forcing a tall image into a square can make an object appear unnaturally wide.

Direct resizing may still be acceptable when:

- the original images have similar aspect ratios,
- the distortion is minor,
- or simplicity is important for the baseline.

We should inspect the result rather than assume it is harmless.

### 5.3 Resize Followed by Crop

Another strategy preserves aspect ratio during resizing and then extracts a fixed-size crop:

```text
resize shorter side
→ crop a 224 × 224 region
```

For evaluation, we commonly use a center crop:

```python
transforms.Resize(256)
transforms.CenterCrop(224)
```

This is deterministic: the same image produces the same evaluated tensor every time.

Its limitation is that the center crop may remove an object near an edge.

### 5.4 Random Resized Crop

During training, `RandomResizedCrop` selects a random region and resizes it to the required dimensions.

This introduces variation in:

- position,
- framing,
- scale,
- and surrounding background.

It can teach a classifier not to depend on one exact object placement.

However, an aggressive crop can remove the evidence needed to identify the label. If only a bird’s background remains, the pipeline may still attach the label `bird`. We have then created a mislabeled training example.

Augmentation is useful only within reasonable boundaries.

## 6. Normalization

### 6.1 What Normalization Does

After tensor conversion, normalization transforms each channel separately:

```text
Normalized value = (Pixel value − Channel mean) ÷ Channel standard deviation
```

Using shorter symbols:

```text
x′ = (x − μ) ÷ σ
```

where:

- `x` is a scaled pixel value,
- `μ` is the channel mean,
- `σ` is the channel standard deviation,
- `x′` is the normalized value.

RGB normalization uses three means and three standard deviations:

```python
transforms.Normalize(
    mean=[mean_red, mean_green, mean_blue],
    std=[std_red, std_green, std_blue],
)
```

The calculation is applied independently to every pixel in its corresponding channel.

### 6.2 A Numerical Example

Suppose a red-channel pixel has a scaled value of `0.80`, and the training set’s red channel has:

```text
mean = 0.50
standard deviation = 0.20
```

Then:

```text
Normalized value = (0.80 − 0.50) ÷ 0.20
                 = 0.30 ÷ 0.20
                 = 1.5
```

The pixel is `1.5` standard deviations above the average red-channel value.

Normalized values are not restricted to `[0, 1]`. Negative values are entirely normal.

```text
Pixel value = 0.30
Mean        = 0.50
Std         = 0.20

Normalized value = (0.30 − 0.50) ÷ 0.20
                 = −1.0
```

The negative result means the pixel is below the channel mean.

### 6.3 Why Normalize?

Normalization generally gives optimization a more stable numeric input distribution.

It can help because:

- channels are brought onto more comparable scales,
- gradients often behave more predictably,
- optimization may converge more smoothly,
- and pretrained models receive inputs similar to those used during pretraining.

Normalization does not make bad data correct, remove bias, or guarantee better generalization. It creates a more suitable numerical representation for training.

### 6.4 Where Should the Statistics Come From?

For a model trained from scratch, we can calculate channel statistics from the **training split only**:

```text
training images
→ estimate mean and standard deviation

validation images
→ reuse the training statistics

test images
→ reuse the training statistics
```

We should not calculate separate statistics for each split.

Using all images—including test images—to calculate normalization statistics lets information from the test distribution influence model development. The leak may appear small, but the evaluation is no longer fully independent.

### 6.5 Pretrained-Model Normalization

A pretrained model expects the preprocessing convention associated with its pretrained weights.

An ImageNet-pretrained model is commonly paired with:

```python
mean = [0.485, 0.456, 0.406]
std = [0.229, 0.224, 0.225]
```

These values are not universal constants. They are part of the pretrained model’s input contract.

```text
Model trained from scratch
→ training-set statistics are a reasonable choice

Pretrained model
→ begin with the preprocessing attached to its pretrained weights
```

When `torchvision` weights provide an official transform pipeline, using that pipeline is safer than manually guessing the expected preprocessing.

## 7. Augmentation as Regularization

### 7.1 The Central Idea

Data augmentation creates temporary, varied versions of training samples while preserving their intended labels. The original image file is not changed.

Suppose our dataset contains one file named `cat_017.jpg`. Across different epochs, the model might receive:

- the original orientation,
- a horizontally flipped version,
- a slightly shifted crop,
- a mildly brighter version,
- or a slightly different scale.

```text
Epoch 1 → slightly cropped cat
Epoch 2 → horizontally flipped cat
Epoch 3 → slightly brighter cat
Epoch 4 → another random crop
```

We have not collected five independent cats. We have created several plausible observations from one source image, and every temporary version retains the label `cat`.

### 7.2 What Problem Does Augmentation Address?

Without augmentation, a powerful model may memorize accidental details:

- the object’s exact position,
- a particular background,
- camera brightness,
- framing,
- or a watermark.

Training performance can become excellent while validation performance remains weaker.

Augmentation acts as regularization because it makes memorization harder. The model must perform under controlled variation.

However, augmentation changes the training distribution. If the variation is unrealistic or label-destroying, it teaches the model the wrong lesson.

### 7.3 Invariance and the Central Rule

An augmentation expresses a belief that the label should remain unchanged after a transformation:

```text
the image changes
but
the correct label does not change
```

For cat-versus-dog classification:

```text
cat image → horizontal flip → still a cat ✅
```

For digit recognition:

```text
digit 6 → rotate 180° → may resemble 9 ❌
```

Every augmentation encodes domain knowledge:

> This visual property may change, but the target meaning should remain stable.

That claim must be justified for the actual task.

### 7.4 Augmentation Does Not Create New Files

The dataset does not need to become:

```text
cat_original.jpg
cat_flipped.jpg
cat_bright.jpg
cat_cropped.jpg
```

Instead, variations are normally created temporarily in memory:

```text
stored image
→ random temporary transformation
→ tensor
→ model
→ temporary result discarded
```

The next time the image is loaded, another variation may be generated.

## 8. Label-Safe and Label-Destroying Transformations

### 8.1 Safety Depends on the Task

There is no globally safe augmentation.

| Task | Transformation | Likely decision | Reason |
|---|---|---:|---|
| Cats vs dogs | Horizontal flip | Usually safe | Species does not depend on facing direction |
| Road-sign direction | Horizontal flip | Unsafe | Left and right may change the instruction |
| Printed-text recognition | Horizontal flip | Unsafe | Mirrored text is not equivalent |
| General object classification | Mild color jitter | Often safe | Object identity usually survives lighting changes |
| Fruit ripeness classification | Strong color jitter | Unsafe | Color may define ripeness |
| Skin-lesion assessment | Aggressive color jitter | Risky | Clinically relevant color may be altered |
| Satellite orientation task | Rotation | Possibly unsafe | North–south orientation may matter |
| Some aerial object tasks | Rotation | Possibly safe | Object class may not depend on orientation |
| Fine-grained bird classification | Aggressive crop | Risky | Distinguishing markings may be removed |

“Commonly used” is not enough justification. We must connect each transformation to the meaning of the label.

### 8.2 The Banana-Ripeness Example

For banana-ripeness classification, color is likely a label-defining feature:

```text
green → often unripe
yellow → often ripe
brown spotting → often overripe
```

Strong color augmentation could make an unripe green banana appear yellow while retaining the original `unripe` label:

```text
image appears ripe
+
label says unripe
=
harmful training example
```

Small brightness or contrast adjustments might still be reasonable if they simulate realistic cameras or lighting without destroying ripeness evidence.

```text
Mild lighting variation
→ may help recognition under different conditions

Strong hue or saturation change
→ may alter the evidence that defines ripeness
```

### 8.3 Common Transforms and Their Risks

#### Horizontal Flipping

Useful when left-right orientation does not change the class.

Risk: directional labels, text, handedness, asymmetric anatomy, or road scenes.

#### Random Cropping

Useful for position and scale variation.

Risk: removing the object or the class-defining region.

#### Rotation

Useful when object orientation naturally varies.

Risk: changing meaning or producing physically implausible examples.

#### Color Jitter

Can vary brightness, contrast, saturation, and hue.

Useful when lighting varies in deployment but color is not the target.

Risk: destroying diagnostic color information.

#### Blur

Can simulate focus or motion problems.

Risk: removing fine details required to distinguish classes.

#### Grayscale Conversion

Can discourage reliance on color.

Risk: destroying information when color is useful or essential.

### 8.4 Augmentation Strength Is a Hyperparameter

Even a sensible transformation can become harmful when applied too strongly or too frequently:

```text
rotation by ±5°
is materially different from
rotation by ±45°
```

Likewise:

```text
brightness change of ±10%
is materially different from
brightness change of ±80%
```

We must choose:

- which transforms to use,
- their magnitude,
- their probability,
- and their combinations.

The best evidence comes from controlled validation comparisons, not merely from whether the augmented images look interesting.

## 9. Training and Evaluation Need Different Pipelines

### 9.1 Training Pipeline

Training transforms may be stochastic:

```text
decode
→ random crop
→ random horizontal flip
→ mild color jitter
→ tensor conversion
→ normalization
```

The same source image can produce a different result each time it is loaded. This is intentional because training should expose the model to plausible variation.

### 9.2 Validation and Test Pipelines

Evaluation transforms should normally be deterministic:

```text
decode
→ fixed resize
→ center crop
→ tensor conversion
→ normalization
```

The same image should produce the same tensor every time.

If validation images receive random crops or flips, the reported metric may vary because the evaluation inputs changed—not because the model changed. This makes comparisons noisy and difficult to defend.

### 9.3 Shared Normalization, Different Augmentation

Training and evaluation should normally share:

- output dimensions,
- channel order,
- tensor data type,
- normalization statistics.

They differ in randomness:

```text
Training:
plausible random variation + shared normalization

Validation and test:
deterministic preprocessing + shared normalization
```

## 10. Transform Ordering

A typical transform order is:

```text
PIL image
→ geometric transforms
→ color transforms
→ tensor conversion
→ normalization
```

Normalization must occur after tensor conversion because it operates on tensor channel values.

A possible training pipeline is:

```python
train_transform = transforms.Compose([
    transforms.RandomResizedCrop(224),
    transforms.RandomHorizontalFlip(),
    transforms.ColorJitter(
        brightness=0.2,
        contrast=0.2,
        saturation=0.2,
    ),
    transforms.ToTensor(),
    transforms.Normalize(
        mean=channel_means,
        std=channel_stds,
    ),
])
```

A corresponding evaluation pipeline might be:

```python
eval_transform = transforms.Compose([
    transforms.Resize(256),
    transforms.CenterCrop(224),
    transforms.ToTensor(),
    transforms.Normalize(
        mean=channel_means,
        std=channel_stds,
    ),
])
```

This is a general-object starting point, not a universal recipe.

Before using it, we must ask:

- Is horizontal flipping safe for our labels?
- Can cropping remove the target?
- Does color carry class information?
- Does the evaluation crop match deployment inputs?
- Are these the correct normalization statistics?

## 11. Datasets and DataLoaders

### 11.1 `ImageFolder`

For folder-based classification, `torchvision.datasets.ImageFolder` expects a structure such as:

```text
train/
├── cats/
│   ├── cat_001.jpg
│   └── cat_002.jpg
└── dogs/
    ├── dog_001.jpg
    └── dog_002.jpg
```

The subdirectory names become class names.

```python
train_dataset = datasets.ImageFolder(
    root="data/train",
    transform=train_transform,
)
```

When we request one item:

```python
image, label = train_dataset[0]
```

the dataset:

1. finds the image file,
2. decodes it,
3. assigns its class index,
4. applies the transform pipeline,
5. returns the transformed tensor and label.

### 11.2 The DataLoader’s Role

The `DataLoader` groups samples into batches:

```python
train_loader = DataLoader(
    train_dataset,
    batch_size=32,
    shuffle=True,
)
```

A batch may have:

```text
images: [32, 3, 224, 224]
labels: [32]
```

Training data is normally shuffled because sample order should change between epochs.

Validation and test data usually do not need shuffling:

```python
validation_loader = DataLoader(
    validation_dataset,
    batch_size=32,
    shuffle=False,
)
```

The `DataLoader` does not augment images itself. The dataset applies its transform whenever a sample is loaded. The loader manages batching, ordering, and loading mechanics.

## 12. A Subtle Dataset-Splitting Problem

Consider this workflow:

```python
full_dataset = ImageFolder(
    root="data",
    transform=train_transform,
)

train_dataset, validation_dataset = random_split(
    full_dataset,
    lengths,
)
```

Both subsets reference the same underlying dataset. Therefore, validation samples also receive `train_transform`.

That is a common bug.

We need separate dataset views or instances:

```text
training dataset instance
→ training transform

validation dataset instance
→ evaluation transform
```

Their sample indices must still define non-overlapping splits.

Real-image split hygiene must also consider related files. Near-duplicate frames, edited copies, or multiple images of the same subject can leak across splits even when filenames differ.

If photographs of the same patient appear in both training and validation, the model may partially recognize the patient instead of generalizing to new patients. We would need a group-aware split by patient rather than a simple image-level random split.

## 13. Visual Inspection Is a Required Test

A pipeline that runs without an exception is not necessarily correct.

Before training, we should inspect transformed samples and verify:

- labels match the visible content,
- the object remains present after cropping,
- orientation is plausible,
- color remains realistic,
- dimensions are correct,
- channels are not swapped,
- and augmentation strength is reasonable.

Because normalization changes the display range, we should approximately reverse it before visualization:

```text
Displayed pixel = Normalized pixel × Standard deviation + Mean
```

Using shorter symbols:

```text
x = x′ × σ + μ
```

This inverse operation is only for interpretation and display. The model should receive the normalized tensor.

We should view multiple transformed versions of the same image. One version may look reasonable by chance; repeated versions reveal the true range of augmentation.

## 15. Interpretation and Limitations

### 15.1 Augmented Samples Are Correlated

Six transformations of one source image do not provide the same information as six independently collected images.

Augmentation can improve robustness, but it cannot replace genuine variation in:

- subjects,
- cameras,
- locations,
- backgrounds,
- populations,
- or acquisition conditions.

### 15.2 Augmentation Cannot Repair Poor Coverage

If the training set contains only daylight road scenes, brightness changes may help somewhat, but they do not faithfully create true nighttime scenes with headlights, reflections, and different sensor noise.

Synthetic variation is limited by the information present in the source images.

### 15.3 Normalization Does Not Remove Dataset Bias

Channel normalization changes numeric distributions. It does not correct:

- class imbalance,
- incorrect labels,
- duplicate images,
- biased sampling,
- or spurious correlations.

A normalized biased dataset remains biased.

### 15.4 Cropping Changes What the Task Means

If the label refers to an entire scene, cropping may remove essential context. If the label refers to a centered object, cropping may be helpful.

A transform cannot be judged separately from the prediction target.

### 15.5 Validation Determines Whether Augmentation Helped

An augmentation gallery tells us whether transformations look plausible. It does not prove improved generalization.

The final evidence comes from a controlled comparison:

```text
baseline preprocessing
versus
baseline preprocessing + justified augmentation
```

We should keep the split, model, training budget, and evaluation procedure fixed while changing the augmentation policy.

## 16. 📌 Chapter Summary

Today we upgraded image loading into a deliberate computer-vision input pipeline:

```text
image file
→ decoded image
→ label-safe spatial and color processing
→ tensor [C, H, W]
→ channel normalization
→ batch [N, C, H, W]
→ model
```

The most important ideas are:

1. `ToTensor()` converts image data into PyTorch’s channel-first representation and usually scales pixels into `[0, 1]`.
2. Normalization applies `(pixel − mean) ÷ standard deviation` independently to each channel.
3. Statistics for from-scratch training should come from the training data, not the holdout set.
4. Pretrained models should receive the preprocessing expected by their weights.
5. Augmentation creates temporary, realistic training variations and assumes the label remains unchanged.
6. Training transforms may be stochastic; ordinary validation and test transforms should be deterministic.
7. Augmentation must be visually inspected and evaluated through controlled comparison.
8. Correct code is not enough—the pipeline must preserve the task’s meaning.

## 18. 🔑 Concept-Check Answer Key

1. The file is decoded into pixels, spatial and possibly color transforms are applied, it is converted to a channel-first tensor, scaled and normalized, and then the `DataLoader` combines samples into a batch.
2. `32` is the number of images, `3` is the RGB channel count, and the two `224` values are image height and width.
3. `ToTensor()` changes the representation and normally scales `0–255` pixels to approximately `0–1`. Normalization then centers and rescales each channel using its mean and standard deviation.
4. `(0.70 − 0.50) ÷ 0.10 = 2.0`.
5. A normalized pixel is negative when its value is below the corresponding channel mean.
6. Using validation or test information during preprocessing design weakens their independence and causes leakage. Their inputs should use statistics learned from training data.
7. A pretrained model learned under a particular input distribution. Its associated normalization is part of the expected input contract.
8. Augmentation makes exact pixel-level memorization harder by exposing the model to plausible variations, encouraging it to learn features that remain stable across them.
9. A flip is safe when left-right orientation does not determine the label, such as many cat-versus-dog images. It is destructive when direction changes meaning, such as left- versus right-turn signs.
10. Deterministic transforms keep the evaluation inputs fixed, so metric changes reflect model differences rather than random image variations.
11. Both subsets reference the same underlying dataset and therefore the validation subset may accidentally receive the stochastic training transform.
12. Code can run while crops remove the object, colors become unrealistic, labels no longer match, or channels are mishandled. Visual inspection exposes these semantic failures.
13. The six versions share the same underlying subject and information. They do not provide the independent variation of six genuinely different examples.
14. Strong hue, saturation, or color changes are concerning because color may define ripeness. Mild brightness or contrast changes may be acceptable only when they preserve the relevant color evidence.
15. Horizontal flips and large rotations are concerning because they can reverse or change the sign’s directional instruction.
