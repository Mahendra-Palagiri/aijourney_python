# Week 14 · Day 2 — The Deep-Learning Training Toolkit

## 1. What we are doing today—and why

Day 1 prepared the **data entering the model**:

Image → augmentation → tensor → normalization → batch.

Day 2 focuses on **how the model learns from those batches**.

You already know the basic training cycle: forward pass, loss, backward pass, and optimizer update. Today we add tools that help control overfitting, training behavior, and model selection.

The goal is not to use every tool automatically. It is to understand **what each tool changes and how to check whether it helped**.

| Tool | What it changes |
|---|---|
| Dropout | Activations used during training |
| Batch normalization | Intermediate feature normalization |
| Weight decay | How weights are updated |
| Learning-rate scheduler | Learning rate over time |
| Early stopping | When training stops |
| Best-model restoration | Which epoch’s model we retain |

We’ll cover the theory here, then implement it through **eight small checkpoints**, separately. This document contains lesson material and small illustrative snippets, not a complete executable program.

## 2. First, introduce validation data

Yesterday we loaded CIFAR-10’s training and test datasets. Today we need a third role: **validation**.

An example split is:

| Dataset | Example size | Purpose |
|---|---:|---|
| Training | 45,000 | Learn model weights |
| Validation | 5,000 | Choose settings, learning-rate changes, and best epoch |
| Test | 10,000 | Final assessment after decisions are finished |

The validation images come from splitting the existing 50,000 training images. **No new download is needed.**

Why not use the test set for early stopping?

Because choosing an epoch based on test performance makes the test set part of model selection. It is no longer an independent final check.

Our transformations remain:

- Training: label-safe random augmentation, tensor conversion, normalization.
- Validation: deterministic preprocessing and normalization.
- Test: the same deterministic preprocessing as validation.

One implementation detail matters: training and validation need **different transform pipelines even though they originate from the same training split**. We’ll use separate dataset objects with disjoint image indices. Simply splitting one augmented dataset would leave validation using its random transforms too.

## 3. Dropout: reduce dependence on particular activations

Suppose a classifier relies heavily on a few activations. It may perform well on training examples but generalize poorly.

Dropout randomly sets some activations to zero **during training**. This encourages the network to learn useful information through multiple paths.

For example:

```python
nn.Dropout(p=0.5)
```

Here, each activation has a 50% probability of being dropped—not necessarily exactly half in every call.

PyTorch scales surviving activations during training:

`surviving output = input ÷ (1 − p)`

With `p = 0.5`, one possible result is:

```text
Input:          [2, 4, 6, 8]
Training output:[0, 8, 0, 16]
Evaluation:     [2, 4, 6, 8]
```

During evaluation, dropout passes its input through unchanged. It does not delete neurons or change tensor shape. [PyTorch Dropout documentation](https://docs.pytorch.org/docs/stable/generated/torch.nn.Dropout)

For our first experiment, a natural location is in the classifier, between a hidden activation and the final output layer.

Too much dropout can make learning harder and cause underfitting. A higher dropout probability is not automatically better.

## 4. Batch normalization: normalize intermediate features

Day 1’s `transforms.Normalize` operates on input-image channels using fixed values we supplied.

**BatchNorm operates inside the model on intermediate features.**

Imagine a convolution produces:

```text
[N, 32, H, W]
```

There are now 32 feature channels—not the original three RGB channels. The corresponding layer is:

```python
nn.BatchNorm2d(32)
```

During training, it computes statistics for each channel across the batch and spatial positions. Conceptually:

`normalized feature = (feature − batch mean) ÷ √(batch variance + ε)`

It then applies a learned scale and offset. Those learned parameters let the model adjust the normalized representation.

With default running-statistics behavior:

- **Training:** uses current-batch statistics and updates running estimates.
- **Evaluation:** uses the accumulated running estimates.

BatchNorm preserves the input shape. A common block is:

```text
Convolution → BatchNorm → ReLU
```

These behaviors are described in the [PyTorch BatchNorm2d documentation](https://docs.pytorch.org/docs/stable/generated/torch.nn.BatchNorm2d.html).

BatchNorm can improve optimization, but it does not guarantee better results. Very small or unrepresentative batches can make its statistics less reliable.

It also **does not replace input normalization**. The two operate at different points in the pipeline.

## 5. Training mode and evaluation mode

Yesterday, we separated training transforms from evaluation transforms. Today, we also separate **model behavior**.

These are independent controls:

| Control | Responsibility |
|---|---|
| Dataset transform | Changes the input image |
| `model.train()` / `model.eval()` | Changes behavior of layers such as dropout and BatchNorm |
| `torch.no_grad()` | Disables gradient recording |

Calling `model.eval()` does **not** switch off random augmentation in your dataset.

Likewise, giving the model deterministic images does **not** switch off dropout.

The usual structure is:

```python
model.train()
# Training batches and weight updates
```

Then:

```python
model.eval()
with torch.no_grad():
    # Validation batches; no weight updates
    pass
```

Two important distinctions:

- `model.eval()` does not itself disable gradients.
- `torch.no_grad()` does not itself put dropout or BatchNorm into evaluation mode.

We use both for ordinary validation.

At the beginning of the next training epoch, we must call `model.train()` again.

## 6. Weight decay: discourage unnecessarily large weights

Dropout acts on activations. Weight decay acts on **weights during optimization**.

A simplified picture of decoupled weight decay is:

`new weight = old weight × (1 − learning rate × decay) − learning update`

The shrinkage discourages weights from growing unnecessarily large.

For our controlled comparison, we can use AdamW in both runs:

```python
# Baseline
torch.optim.AdamW(model.parameters(), lr=0.001, weight_decay=0.0)

# Weight-decay experiment
torch.optim.AdamW(model.parameters(), lr=0.001, weight_decay=0.0001)
```

These are illustrative starting values, not guaranteed optimal settings.

AdamW applies weight decay separately from its adaptive gradient update. This is why weight decay with AdamW should not simply be described as identical to adding an L2 penalty to Adam’s loss. [AdamW paper](https://arxiv.org/abs/1711.05101)

Too much decay can constrain the model excessively. We judge it through validation results, not by whether the weights became smaller.

## 7. Learning-rate scheduling: change the update size over time

The learning rate controls the size of optimization steps.

A learning rate that works well early in training may be too large for later refinement. A scheduler changes it according to a rule.

For today, we’ll use the idea behind `ReduceLROnPlateau`:

> If validation loss stops improving, reduce the learning rate.

For example:

```text
Current learning rate: 0.001
Reduction factor:      0.5
New learning rate:     0.0005
```

This scheduler receives the completed epoch’s validation metric:

```python
scheduler.step(validation_loss)
```

For loss, lower is better, so its mode is `"min"`. Its patience controls how long it tolerates a lack of improvement before reducing the learning rate. [PyTorch ReduceLROnPlateau documentation](https://docs.pytorch.org/docs/stable/generated/torch.optim.lr_scheduler.ReduceLROnPlateau.html)

The scheduler does not directly change weights or stop training. It changes the learning rate used by subsequent optimizer updates.

We’ll record the learning rate each epoch so its effect is visible.

## 8. Early stopping—and restoring the best epoch

Early stopping asks:

> Has validation performance stopped improving for long enough that further training is no longer worthwhile?

We track:

- Best validation loss so far.
- Which epoch achieved it.
- Consecutive epochs without sufficient improvement.
- A patience limit.

A small `min_delta` can define how much improvement is meaningful.

Consider these illustrative results:

| Epoch | Training loss | Validation loss |
|---|---:|---:|
| 1 | 1.80 | 1.70 |
| 2 | 1.40 | 1.35 |
| 3 | 1.10 | 1.20 |
| 4 | 0.90 | 1.24 |
| 5 | 0.75 | 1.29 |

Training loss continues falling, but validation loss is best at epoch 3.

If we stop after epoch 5, we should **restore the saved model from epoch 3**, not automatically retain epoch 5.

Stopping and restoration are separate responsibilities:

- Early stopping decides when to finish.
- Best-model restoration selects the model to keep.

The saved state must be a genuine snapshot. We’ll handle that carefully when implementing it.

Also, scheduler patience and stopping patience must cooperate. If we stop immediately when progress stalls, the scheduler has no opportunity to reduce the learning rate and let training recover.

## 9. How one epoch fits together

Our expanded training process is:

```text
Enter training mode
    ↓
Train over batches and update weights
    ↓
Enter evaluation mode
    ↓
Calculate validation metrics without gradients
    ↓
Record losses, accuracy, and learning rate
    ↓
Save a best-model snapshot when appropriate
    ↓
Update the scheduler and stopping decision
    ↓
Continue, or stop and restore the best model
```

Validation influences our decisions, but **validation batches do not perform backward passes or optimizer updates**.

For epoch loss, we’ll accumulate batch loss weighted by the number of images. That avoids giving a small final batch the same influence as a full batch.

## 10. How we will judge the results

We’ll plot training and validation loss and record validation accuracy.

Typical patterns include:

| Observation | Possible interpretation |
|---|---|
| Training and validation losses both fall | Learning is progressing |
| Training loss falls while validation loss rises | Possible overfitting |
| Both remain high | Possible underfitting, optimization trouble, or a bug |
| Loss becomes unstable | Investigate learning rate, inputs, gradients, and implementation |

These are clues, not automatic diagnoses.

Also, validation loss can be lower than training loss. Training may include difficult augmented images and active dropout, while validation uses cleaner inputs with dropout disabled.

A single run cannot prove a small improvement is reliable. We’ll keep the split and experimental settings controlled and treat tiny differences cautiously.

## 16. Concept-check answer key

Try the questions before reading the answers.

### 16.1 Answers to the first concept check

1. **Validation versus test:** validation supports model selection, scheduling, and stopping decisions. Test data is reserved for a final assessment after those decisions. Repeatedly choosing settings based on the test set compromises its independence.
2. **Validation augmentation:** not for our standard validation protocol. Use deterministic preprocessing, without random flips or rotations. This makes epoch-to-epoch comparisons more consistent.
3. **Model mode versus transforms:** no. `model.eval()` changes the behavior of relevant model layers, not the dataset’s transformation pipeline.
4. **Which epoch:** retain the saved model from epoch 4, because it achieved the best validation loss under the stated selection rule.

### 16.2 Answers to the additional concept checks

1. **Permanent removal:** no. Dropout temporarily zeros randomly selected activations during training; it neither deletes neurons nor guarantees exactly half are zeroed on every call.
2. **Surviving activation:** `6 ÷ (1 − 0.5) = 12`. A dropped activation would instead become zero.
3. **BatchNorm channel count:** 32. The feature count corresponds to the channel dimension, not batch size or spatial size.
4. **Two types of normalization:** no. Input normalization uses supplied constants on image channels. BatchNorm operates on intermediate feature channels, uses batch statistics during training and default running estimates during evaluation, and learns a scale and offset.
5. **No-grad behavior:** no. It disables gradient recording. Use `model.eval()` as well for ordinary validation so dropout and BatchNorm behave appropriately.
6. **Decay versus scheduler:** weight decay shrinks weights during optimization. A scheduler changes the learning rate used by future optimizer steps. Neither is an early-stopping mechanism.
7. **Patience interaction:** training needs additional epochs after a learning-rate reduction to show whether the smaller updates help. Stopping too soon prevents that opportunity.
8. **Lower validation loss:** training may use augmented, harder images and active dropout; validation uses deterministic inputs and inactive dropout. The difference alone is not evidence of a bug.
9. **Controlled comparisons:** simultaneous changes obscure which tool caused the result. One-factor comparisons support clearer conclusions before testing a combination.
10. **Final versus best:** validation performance can deteriorate while training loss keeps improving. Restore the checkpoint selected by validation performance rather than assuming the last weights are best.
