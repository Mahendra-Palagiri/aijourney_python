## 🧠 Core Concept

A real model-building workflow should not begin with the most complex model.

We first define the problem and create a simple baseline. Then we build a better model and compare it fairly.

For Week 12, the project flow is:

```text
problem → data → baseline model → baseline evaluation → improved model → improved model evaluation → comparison → retrospective
```

The improved model is not the whole capstone. The full workflow is the capstone.

---

## 🧩 Capstone Problem

We will work on an image-classification problem.

The model will receive an image and predict the correct class label.

General flow:

```text
image tensor → model → class scores/logits → predicted class
```

The exact dataset may be simple, but the workflow should be professional:

- frame the problem
- inspect the data
- understand tensor shapes
- build a baseline
- train and evaluate the baseline
- build an improved model
- train and evaluate the improved model
- compare results
- explain what happened
- write a retrospective

---

## 🧱 Modeling Strategy

### 1. Baseline Model — Fully Connected Neural Network

The baseline model will flatten the image first.

```text
image → flatten → Linear → ReLU → Linear → logits
```

This model treats the image as a flat list of numbers.

It gives us a simple reference point.

We need this baseline because we cannot honestly say the CNN is better unless we compare it against something simpler.

---

### 2. Improved Model — Image-Aware Neural Network

The improved model will keep the image structure longer.

```text
image → Conv2d → ReLU → Pool → Conv2d → ReLU → Pool → Flatten → Linear → logits
```

This model is better suited for image data because it can use local spatial patterns instead of immediately treating all pixels as unrelated features.

We should not assume it is better just because it is more advanced. We will evaluate it using the same workflow and compare the evidence.

---

## ⚖️ Why We Compare Models

Model comparison is one important part of the Week 12 workflow.

We are not only asking:

```text
Can we train a more advanced model?
```

We are asking:

```text
Can we build, train, evaluate, compare, and explain models using a clean PyTorch workflow?
```

This matters because a more complex model is not automatically better.

The improved model should justify its added complexity through better validation/test performance, better learning behavior, or a clearly explained tradeoff.

---

## 📏 Evaluation Plan

We will evaluate both models using the same discipline:

- same dataset
- same train/validation/test split
- same evaluation metric
- same basic training loop structure
- same comparison table

Primary metrics:

- training loss
- validation loss
- training accuracy
- validation accuracy
- final test accuracy

Final comparison table:

```text
Model | Train Loss | Val Loss | Train Accuracy | Val Accuracy | Test Accuracy | Notes
```

## 🛠️ Model, Loss, and Optimizer Choices

The choices must be explicit and justified.

### Model Choice

- Baseline model: simple fully connected neural network
- Improved model: image-aware neural network

Reason:

- the baseline gives us a simple reference point
- the improved model tests whether a more suitable architecture improves performance

### Loss Function

Expected loss:

```text
CrossEntropyLoss
```

Reason:

- this is a multi-class classification task
- the model outputs logits for each class

### Optimizer

Expected optimizer:

```text
Adam or SGD
```

Reason:

- the optimizer updates model parameters using gradients
- the choice should be documented before training
- if we use the same optimizer for both models, comparison is simpler
